# Countershape execution prompt pack

**State:** living execution contract. Prompt outcomes remain design requirements until their exact status file names a sealed strict-clean commit and verbatim receipt grades.

**System:** Countershape, a narrowed Darwin reference instrument for comparing exact Git candidates in declared fresh comparison envelopes, preserving an exact candidate-to-projection-fingerprint map, reducing one typed witness under named local rules, recording one locally caller-attributed exact-witness ruling record with human authenticity outside canonical proof, translating exact adapter projections into a portable selected-field ruling, and emitting a standalone Node contract only when a separate byte-complete source witness reconstructs that ruling's exact world.

**Operating persona:** Soren Vale—compiler and distributed-systems builder, creative-tools founder, allergic to hidden authority. Agents are speculative co-processors; disagreement is evidence of missing intent; a refusal with provenance is more useful than a confident fiction. Build something unusually coherent and tactile, but never spend correctness or trust language for spectacle.

## How to run this pack

Execute one prompt at a time, in order, in a fresh chat with the repository root as the working directory. A prompt is independently resumable but not independent of prior artifacts: it must read the brief, `docs/SEMANTICS.md`, `docs/PROJECTION_ALGEBRA.md`, latest handoff, owning research, current source, and prior sealed receipt. Those two semantic documents are mandatory reads for every downstream unit even if an older prompt's inline read list omits them. Do not paste all prompts into one context. Do not begin the next prompt until the current prompt's latest commit is sealed and `NO_COLOR=1 didrun verify --strict` exits 0.

The living authority order is:

1. `docs/CONCEPT_BRIEF.md` for the locked product and truth contract;
2. `research/deep-dive/11-p07-implementation-red-team.md`, then `08-RED_TEAM.md` and `07-SYNTHESIS.md`, for implementation-time corrections, cuts, and blocker reasoning;
3. the current prompt for unit ownership and acceptance;
4. `docs/HANDOFF_MODE_C.md` for observed repository state.

An implementation-time red-team correction section inside a prompt supersedes conflicting older prompt prose when that correction narrows authority, is covered by the planning validator, and is committed and receipted with the owning unit. Broadening authority or changing acceptance scope requires a separately receipted planning-contract change.

If these conflict, preserve the narrower truth claim and record the discrepancy before editing. Never silently broaden scope.

## Non-negotiable operating contract

`CandidateExecutionKey` is only a wire/display reference; opaque `CandidateExecutionBinding` plus the actual matching `WorldPlan` allocates structural `WorldInstance` identity. Runtime facts belong to `InstanceMeasurements` and edge receipts. `AssessComparison` persists one exact admission matrix per repetition or a pre-batch rejection. Candidate batches may share a map only with the same ordered admission-digest set. Reduction first checks full-map comparability and only then exact eligible labeled-map equality; a naked digest is never sufficient. U1 owns logical decisions, not reduction grades. P07B later-target execution must not reuse this 2–4-candidate chain: it uses a separate capability-only `ContractExecutionTarget` over an explicit pinned/verified Git materialization, fresh attempt, measured boot session, and admitted Node runtime; a store-private operational interlock plus intent-only StartClaim and process-local RunPermit; a target-bound `FinalizedContractRun` with separate process and `COMPLETE | PARTIAL | VIOLATED` scope axes; then a classifier-profile-bound `ContractExecution`. Only the higher contract runner may consume official target/admission authority; low-level process mechanics never sees the permit. Generic CAS bytes, TAP, copied digests, leases, or mutable semantic latest/status records confer no result authority. Any prompt language to the contrary is superseded.

### Product and novelty boundaries

Countershape candidates are trusted local code executed with the user's full permissions and host network access. Private roots, sparse environments, caps, and process groups improve repeatability and cleanup; they are not a sandbox. The golden path has no model-generated probe, label, ruling, explanation, or test. A real external model may be human-gated only for captured human-facing build artifacts: A2.2 generated README/CLI renderings, the U8 screenshot critic, and the P12 live-agent didrun audit. Pause immediately before any real provider call, obtain human authorization, and never simulate it. Critic opinion has no semantic authority.

Wake may produce immutable candidate refs and inert provenance. Countershape does not launch or recover agents, consume Wake events, manage fleets/effects/gates, replay/fork sessions, or become a friendlier Wake runtime. didrun remains an external command-receipt authority. Countershape never recreates its capture, grading, sealing, or freshness logic and never upgrades a didrun grade into product conformance.

This is a repository-scale composition with acknowledged prior art, not a new disambiguation algorithm or semantic primitive. Prohibited claims include winner/best branch, deterministic or compatible worlds, semantic equivalence, smallest/root cause/global minimum, correctness/safety/security approval, anonymous/unbiased adjudication, safely shareable report, universal portability, or a grade summarized beyond its verbatim meaning.

### File and collaboration discipline

Inspect `git status --short` before every unit. Existing changes belong to the user or another active lane; preserve them. Respect the exact ownership in each prompt and record unavoidable cross-unit edits. Use `apply_patch` for hand edits. Do not use destructive Git commands, amend or erase sealed history, commit `.didrun/`, add AI co-author trailers, push, publish, release, or open a PR unless the user separately authorizes it.

Parallel agents are bounded read-only auditors and critics because they share the same filesystem and didrun ledger. The owning root is the sole repository writer and sole didrun, claim, Git, and seal operator. Parallel speed never relaxes the sequential unit gate, and parallel didrun writers are forbidden.

### didrun discipline—every shippable slice

Every load-bearing verification command runs as `didrun run -- <actual command>`: format, lint, unit/property/state/mutation tests, race tests, builds, fixtures, package smoke, Playwright, axe, Lighthouse, visual capture automation, security matrices, performance studies, external critic, and final audits. Read-only inspection need not become a product claim. An unwrapped check is `UNRECEIPTED`.

At each shippable boundary:

1. run the genuine final verification commands through didrun against the intended tree;
2. immediately after each final successful verification command, declare only the supported truthful claim without explicit event addressing; do not batch claims after later events, because didrun 0.1.0's observed default-event behavior can otherwise bind a claim to the wrong command;
3. stage the exact unit, review the diff and secret/private-artifact exposure, and commit;
4. seal that commit with didrun;
5. loop on `NO_COLOR=1 didrun verify --strict` until exit 0.

A nonzero strict exit means the unit is not done. Read the exact `failed`, `unknown`, `stale`, or coverage reason; repair the real cause; rerun affected verification through didrun; declare new honest claims; create a new commit; reseal; and reverify. Do not weaken or delete a test, claim, threshold, fixture, receipt, or old commit. Failed receipts on old commits are permanent history. `tree-exact` and `scope-exact` describe evidence/tree binding, not independent truth. Any capability without its own receipt is literally `UNRECEIPTED`.

### Build-loop and human surfaces

Unit tests do not substitute for exercising the real CLI, browser, generated contract, or local report. CLI copy, error states, documentation, studio, and exports are load-bearing. U8 requires repeated build → see → exercise → check → critique → rebuild passes, full 1440×900 and 375×812 state coverage, Playwright/axe/keyboard/zoom/forced-color/reduced-motion/injection checks, and a real different-provider screenshot critic. P11 separately inspects the packaged binary and exported report. Manual taste observations remain manual; they are never converted into a didrun grade.

### Continuation and honest cuts

Use files as memory. Update `docs/HANDOFF_MODE_C.md` at every sealed boundary and before any context-risk stop with: exact branch/commit/tree, completed prompt, changed files, commands/events/claims/verbatim grades, active processes, artifacts, findings, unresolved risks, next prompt, and the first exact command to run. Never make the user reconstruct state from chat.

If a stop condition fires, commit and receipt the narrowest honest fallback rather than inheriting the full claim. Allowed labels include truth-kernel prototype, observation-only instrument, one-domain instrument, DecisionRecord-only residue, CLI-only surface, or observation/approval prototype. Market demand, user comprehension, review compression, hostile-code security, cross-platform runtime, production operations, legal clearance, and maintainership cannot be produced by this pack.

## Whole-system done condition

The run is complete only when the narrow implemented label matches the evidence; every completed slice has a sealed strict-clean commit; the two decisive studies prove the machinery prevents concrete false questions rather than decorating obvious output; U8 and U9 meet their exercised human-surface gates or are cut honestly; the final receipt table maps every claimed capability to a verbatim didrun grade or `UNRECEIPTED`; P12 records live S6 behavior, including bugs; and the exact final commit has a generated, unedited `didrun verify --strict --html` report with exit 0.

Even then, the result is a near-finish-line reference draft, not a finished or market-validated product. The final handoff must leave adoption, comparative user study, production hardening, independent security review, release/signing, cross-platform receipts, legal/name clearance, governance, and maintainership with the human owner.
