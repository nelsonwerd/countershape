# didrun live-session findings

This file records didrun behavior observed during a real multi-agent build. It is not a replacement for the final S6 report. Raw ledgers and captured command output remain local and ignored because didrun evidence is secret-bearing by construction.

## S6-01 — Concurrent writers fork one session chain

- **Observed:** the pre-commit session contained 14 JSONL entries. Structural inspection found duplicate indices `2` and `7`; `didrun show --session` reported `chain BROKEN at index 2`.
- **Preserved evidence:** the original `session.log` SHA-256 is `623be68cc7a55fcf1245a41ed138a86798a2abc744093ed8a8acb08041125e0e`. The complete original `.didrun` directory is preserved locally under `.didrun-history/2026-07-14-precommit-concurrent/` and is ignored from Git.
- **Mechanism:** source inspection of the installed editable package shows `Session.append()` reads the current tail with `_last()` and then opens the log in append mode, with no process lock or atomic compare-and-append. The duplicate indices are consistent with two agents reading the same tail before either append became authoritative.
- **Impact:** the original ledger is not valid evidence. No claim will be declared over it and it will never be sealed.
- **Historical run policy:** didrun writes were serialized by the primary agent and a fresh ledger was used after preserving the failed history. At that point subagents were still allowed to edit in parallel. S6-07 supersedes that policy: subagents are now read-only critics, while the primary agent serializes repository edits, build commands, Git, and every didrun operation.
- **Suggested fix:** take an interprocess lock around tail read plus append, then re-read the tail after acquiring it. Add a stress test that launches concurrent writers and requires one contiguous, intact chain.

## S6-02 — Failed wrapper output is not surfaced by the CLI

- **Observed (historical pre-sparse invocation):** the early command `didrun run -- node tools/validate-planning.mjs` correctly returned exit code 1, but the terminal only printed didrun's event summary. It did not relay the wrapped command's stdout or stderr. The same happened on successful wrapper event 18 while calculating an independent SHA-256 golden: the event was recorded with exit 0, but the digest text was not visible through either `didrun run` or `didrun show --session`. The ambient command spelling is preserved only as history and must not be copied into a current verification profile.
- **Observed under long real verification:** U4 mutation event `415` ran for 201.95 seconds and repeated-study event `416` ran for 332.42 seconds. Final-tree repeated-study event `459` ran for 447.77 seconds, inherited U2 mutation event `460` for 366.42 seconds, inherited U3 mutation event `461` for 530.21 seconds, and U4 mutation event `463` for 270.12 seconds. None surfaced bounded child progress while running; only the durable wrapper summary appeared after completion. This is safe for evidence retention but poor for a human supervising a long agent session, because silence is indistinguishable from a stuck verifier until the final event arrives.
- **Read-only diagnosis:** inspect the affected event in `.didrun/session.log`, resolve its `stdout_blob` and `stderr_blob` digests, and read the corresponding immutable objects under `.didrun/objects/<digest>`. This recovers the already-recorded wrapped output without manufacturing a second execution. Blob inspection is diagnosis only: it is not a verification event, receipt, claim, seal, or substitute for a successful didrun-wrapped rerun after a real fix.
- **Object-layout footnote:** this didrun workspace mixes Git-style fanout directories and full-digest flat wrapper blobs under `.didrun/objects`. For a wrapper event's `stdout_blob`/`stderr_blob`, the observed retained output path is the flat full SHA-256 name. A future inspection command should hide this implementation detail rather than require agents to infer the object layout.
- **Prohibited workaround:** never rerun a load-bearing command unwrapped merely to see its output. If didrun fails to retain or expose the referenced blob, record that as a didrun bug and keep the affected capability `UNRECEIPTED`.
- **Impact:** an agent cannot diagnose a recorded failure from the command response or `didrun show`; the captured blobs exist but the CLI exposes no safe output-view command. Long successful checks also provide no progressive liveness signal to the supervising human.
- **Run policy:** diagnose only by inspecting the immutable blobs already referenced by the recorded event. After repairing the real fault, rerun the load-bearing command through didrun; an unwrapped diagnostic rerun is never used.
- **Suggested fix:** tee bounded redaction-aware progress while still capturing immutable output, and provide `didrun show --event N --output` plus an explicit running-event heartbeat.

## S6-03 — Root `.didrun/` ignore defeats didrun's tree digest

- **Observed:** on the unborn repository, two successful wrapped validator commands recorded `tree (none)`. Reproducing didrun's temporary-index command showed `git add -A -- . ':(exclude,top).didrun' ':(exclude,top).didrun/**'` returning 1 with “The following paths are ignored: .didrun” when the root `.gitignore` contained `.didrun/`.
- **Control:** removing only that redundant root rule while retaining didrun's own `.didrun/.gitignore` changed the same probe to exit 0 and produce a tree id. `git status --ignored` and `git check-ignore` still show all ledger content ignored. didrun's source also excludes `.didrun` explicitly from every tree digest.
- **Impact:** the apparently recommended defense-in-depth ignore rule makes otherwise successful evidence unbindable (`unknown`) in didrun 0.1.0.
- **Run policy:** rely on didrun's generated self-ignore plus its explicit digest exclusion for the live ledger; keep archived ledgers under the separately ignored `.didrun-history/`. Before every commit, inspect the staged set and refuse any `.didrun` path.
- **Suggested fix:** make the temporary-index add tolerate an explicitly ignored excluded root, and add a fixture whose repository-level `.gitignore` contains `.didrun/`.

## S6-04 — Wrapped commands inherit false-green environment controls

- **Observed:** `didrun run --` records the child argv and result but does not establish a clean child environment. Ambient Go controls such as `GOFLAGS=-run=^$` or `GOFLAGS=-exec=/usr/bin/true`, and Node preload controls such as `NODE_OPTIONS`/`NODE_PATH`, can change or bypass the named verifier while leaving a superficially successful wrapper event.
- **Impact:** an absolute executable alone is insufficient. A command receipt can describe exactly what didrun launched without proving that inherited tool-specific controls were absent.
- **Run policy:** every load-bearing U1 Go/Node command uses `/usr/bin/env -i`, absolute tool paths, fixed HOME/TMP/cache roots, `GOENV=off`, `GOWORK=off`, `GOTOOLCHAIN=local`, `GOPROXY=off`, explicit empty `GOFLAGS`, and no `NODE_OPTIONS` or `NODE_PATH`. The mutation driver additionally fingerprints its operator-declared Go executable. No ambient receipt is claimed.
- **Suggested fix:** support a declared clean-environment mode in didrun and include the effective allowlisted environment in the event body, with secret values structurally excluded.

## S6-05 — Timed Go fuzz teardown can record a false-red

- **Observed:** serialized wrapper event `101` ran `FuzzObservedSelectionAlwaysDerivesTheExactComplement` for the declared 20 seconds, completed baseline coverage and 22,907 fuzz executions, reported no panic, assertion, crashing input, or failing corpus, then exited 1 at 20.11 seconds with only `context deadline exceeded`.
- **Diagnosis boundary:** this is consistent with a Go 1.26.5 timed-fuzz coordinator cancellation race during deadline teardown; it is not evidence that the property passed, and it is not attributed to didrun. The failed event remains permanent and unclaimed.
- **Repair and run policy:** fixture construction was moved outside the per-input callback, the exact-complement assertion was strengthened from cardinality to exact outcome-ID set equality, and the same target must pass again for at least 20 seconds through didrun. If native parallel timed fuzzing repeats the teardown race, retain the false-red and rerun with declared `GOMAXPROCS=1` plus `-parallel=1`; this changes scheduling pressure, not the property or duration. Never relabel the failed receipt as success.
- **Upstream tail:** a production evidence policy should pin a Go release with a verified coordinator fix or prefer an execution-count fuzz budget whose completion does not race a parent deadline. Countershape does not claim to repair the Go toolchain.

## S6-06 — Entropy scanning blocks ordinary cryptographic fixtures

- **Observed:** the first U1 seal attempt for commit `13282ed` stopped with `export blocked: 104 likely secret(s) found (high-entropy)`. U1 intentionally contains many fixed SHA-256 digests, candidate keys, canonical golden values, and evidence identifiers; didrun 0.1.0 reported only the aggregate count and no safe path/line classification with which to distinguish those fixtures from an actual credential.
- **Response:** the blocked attempt remains part of the live session history. After manually reviewing the staged inventory and repository for credential-bearing files, the exact commit was sealed with `didrun seal --commit 13282ed --allow-secrets`. The resulting strict report truthfully displays `sealed with --allow-secrets (redacted export)`; Countershape does not reinterpret that notice as a secret-free finding.
- **Continued live evidence:** later plain seals were blocked by 127 findings at U2, 86 at U3, 121 at U4, and 66 at U5. Each unit first passed an exact staged inventory, staged diff check, and scoped credential-prefix scan, then used the logged redacted-export override. The variation tracks ordinary source/digest/mutant content and does not make the aggregate detector output more actionable.
- **Impact:** entropy alone produces high false-positive pressure in cryptographic and receipt-heavy repositories, while the aggregate message provides too little locality for a precise repair. The override also coarsens the final evidence statement: it says export redaction was requested, not whether every flagged value was benign.
- **Run policy:** never use `--allow-secrets` automatically. First inspect the exact staged path inventory and obvious credential filenames/patterns; then record the override verbatim in status and handoff. Public export or repository publication still requires a dedicated human secret scan outside didrun.
- **Suggested fix:** emit a redacted finding list with file, line, detector kind, and a stable finding fingerprint; support explicit allowlisted fixture regions or semantic digest types without displaying the suspected value.

## S6-07 — A second concurrent append breaks claim-address stability and can evade strict

- **Observed:** during the P07 planning gate, the primary orchestration mistakenly launched the generator and validator syntax checks through didrun concurrently. The two executions began within one millisecond and both appended stored event index `865` with the same predecessor hash. The next event continued from only one sibling. The resulting log has 906 physical entries but ends at stored index `904`; `didrun show --session` exits `1` with `chain BROKEN at index 865`.
- **Preserved evidence:** the complete failed ledger is retained byte-for-byte under `.didrun-history/2026-07-15-p07-concurrent/.didrun/`. Its `session.log`, `claims.jsonl`, `seals.jsonl`, and failed P07 HTML report have SHA-256 digests `b404c7e96e48b120ece05377133f04f9b89b8426c7c86a6cd16a7e8fcee56934`, `f517ddf60e8079e839e06c6809c7d4575874f75dc28a190f504d0782a5fd7d87`, `579e0178d53f1cce22b8497c9e4fdc28f0a045a5a8e4617c56ef0729b973fe5b`, and `84be82d9cef62fc60dbb94713a40200b15574eb864bce9539c7b159fc2b90c7c`, respectively. Commit `e2cc2aa80f19` and its failed Git-note manifest remain untouched.
- **Mechanism:** `Session.append()` reads the current tail and then appends without an interprocess lock. `didrun show --session` displays the stored `ChainEntry.index`, while explicit claims are graded by treating the supplied number as an offset into the physical `Session.events()` list. Stored index `865` is ambiguous at physical offsets `865` and `866`; each subsequent unique stored index `N >= 866` lives at physical offset `N+1`.
- **Receipt consequence:** the final generator claim supplied displayed index `891`, but the grader resolved physical offset `891`, stored event `890`, which was the failed staged whitespace check. Every later final label was similarly shifted one command backward. The failed P07 manifest reports `13/28 claims recorded-exact`, but its 13 positive rows are semantically misbound and support no named capability. The other 14 rows are stale and one is failed. All 28 claims are unusable.
- **Fail-open consequence:** `seal` and `verify --strict` load physical events but do not first call `verify_chain()`. A later manifest could therefore print `ALL RECORDED-EXACT` on a broken ledger. Countershape will not use such a mechanically green result as evidence.
- **Historical-prefix boundary:** sealed U1–U6 manifests precede the fork and retain their previously reported grades against the intact `0`–`864` prefix. The fork invalidates post-fork P07 claim addressing and the chain as a whole; it does not retroactively turn those earlier commit-bound manifests into P07 evidence or erase their archived prefix.
- **Response:** preserve the forked ledger and failed manifest; start a fresh ledger; serialize every didrun invocation through the primary agent; and bind a claim immediately after its successful command without an explicit event number. Parallel agents are restricted to bounded read-only review. Build, mutation, Git, claim, seal, and verification operations are never parallelized.
- **Suggested fix:** lock tail-read plus append and retry atomically; bind claims by immutable entry hash or another stable unique identifier rather than a list offset; reject duplicate stored indices; make seal and strict verification fail closed on a broken chain; and regression-test concurrent producers.

## Evidence boundary

These are live product findings, not proof of adversarial tamper resistance, platform portability, or behavior outside this macOS session. Both broken ledgers are retained as history rather than rewritten, repaired, or used to support a capability claim.

## S6-08 — Strict includes stale exploratory claims from the whole live ledger

- **Observed:** the P07A translator source commit `d274588b3aba` sealed with fifteen final tree-exact claims, but its manifest also inherited sixteen claims declared on earlier source trees in the same chain-intact ledger. `NO_COLOR=1 didrun verify --strict` exited `1` with `15/31 claims recorded-exact` and marked the earlier sixteen rows `STALE`.
- **Expected and useful behavior:** strict correctly refused to call the mixed manifest clean. The stale claims were not deleted, narrowed, or relabeled, and the source commit was not resealed because `didrun seal` replaces its Git note.
- **Operational friction:** didrun has no explicit unit-close or claim-supersession primitive. During a multi-pass build, honest intermediate claims remain part of every later seal in that session even when final replacements are exact. A strict shippable boundary therefore requires either never claiming until the very end or preserving the iterative ledger and starting a fresh ledger for a follow-up receipt commit.
- **Response:** preserve the complete source ledger under `.didrun-history/2026-07-15-p07a-translator-stale/.didrun/`; keep its failed manifest as negative history; create a follow-up documentation boundary; rerun the load-bearing gates against that exact tree through a fresh serialized ledger; seal once; and require both chain integrity and strict exit `0`.
- **Suggested improvement:** support an immutable claim-generation or unit identifier and allow `seal` to select one closed generation while retaining prior generations as visible negative/history rows. Never silently discard claims, and continue making a mixed-generation strict seal nonzero by default.

## S6-09 — Aggregate entropy findings conflate workspace paths and test identifiers with credentials

- **Observed:** the first P07A-B source seal for commit `65005e498b05` stopped with `60 likely secret(s) found (high-entropy)`. The CLI again exposed only detector kind and aggregate count.
- **Masked-source classification:** a local diagnostic used didrun's own scanner over only the 17 claim-bound events and reported 39 argv findings plus 21 stdout findings. All 39 argv findings were recorded workspace/toolchain verification paths or Countershape command identifiers. All 21 stdout findings were identifiers present verbatim in the checked-in mutation manifest. The scanner reported zero AWS, GitHub, Slack, OpenAI, PEM, or secret-assignment pattern findings.
- **Response:** the classification diagnostic emitted only source categories and counts; no suspected credential value was reproduced in this document. After exact staged-tree checks and the masked classification, the source commit sealed with the logged `--allow-secrets` redacted-export override and strict exited `0` with `17/17 claims recorded-exact`. This is not a secret-free finding, a credential audit, or permission to publish the ledger.
- **Impact:** the override path works under a real long agent session, but high-entropy false positives remain common and the aggregate message forces local source-level diagnostics to justify an override. That diagnostic is easy to get wrong and is not a safe product interface.
- **Suggested improvement:** report detector kind, event index, source class (`argv`, stdout, or stderr), and a stable masked finding fingerprint. Recognize declared workspace/cache/toolchain paths and checked-in test identifiers without printing their raw values. Keep structured credential detections fail-closed and separate from heuristic entropy counts.
- **P07B-A1 continuation evidence:** the plain seal for source commit `1e56da3bfafc` stopped with `105 likely secret(s) found (high-entropy)`. Before overriding, the unit passed its exact 34-path staged inventory/diff gate and a scoped structured credential-pattern scan over the exact staged blobs; that scan found no match in its named pattern set. The commit then sealed with the logged `--allow-secrets` redacted-export override, and strict exited `0` with `15/15 claims recorded-exact`, every row verbatim `TREE-EXACT`. This does not establish secret absence or authorize public ledger export. It confirms that the aggregate false-positive friction persists under a larger ordinary source/mutant workload.
- **Live serialized-session behavior:** P07B-A1 recorded each final verification and immediate claim through one root writer. The chain remained intact and strict-clean; no concurrent-writer symptom occurred. This supports the serialized operating discipline only, not general multi-process safety.

## S6-10 — Git-note attachment failure advances local seal state fail-open

- **Observed:** the first P07B-A2.1 `seal --allow-secrets` invocation printed a complete `15/15` result and returned `0`, but the managed sandbox denied the write to `refs/notes/didrun`. didrun still appended its local seal row and advanced the seal watermark. An immediate strict verification then exited `1` with `NO CLAIMS` because the commit had no didrun Git note.
- **Preserved evidence:** the complete false-publication state is retained under `.didrun-history/2026-07-16-p07b-a2-1-note-attach-failure/.didrun/`. Its `session.log`, `claims.jsonl`, and false `seals.jsonl` SHA-256 digests are `3888ace8db7e443e2608275a3c910a5b69d64972e2ed002c89c8ac4b92d64ea7`, `a323c43643beb647fa352b01f620dc1a9d9dc53b77035b672480c62998e64cb8`, and `f278ae54e157a2311de9ccc251a656751186fe41b491e6809432b54a2a38ef27`; its object-set digest is `291463578db6fbff1b6354b7c0649306a192b4e186389307b7e7cd8986bd4d29`.
- **Mechanism:** installed didrun's note-attachment path does not fail the seal when `git notes add` returns nonzero, while local seal state is recorded independently. The external sandbox denial is not a didrun defect; accepting that denial as a successful publication and advancing the watermark is.
- **Recovery:** the false state was preserved unchanged. A recovery ledger copied the session, claims, objects, and self-ignore byte-for-byte, omitted only the false local seal row, and verified the copied digests. The same commit/tree/claims were then sealed with explicit Git-note write authority; `git notes --ref=didrun show HEAD` existed and strict exited `0`. All seals in this managed environment now require that authority.
- **Impact:** `seals.jsonl` and a zero seal exit can disagree with public commit-bound evidence. An interrupted agent could report a unit as sealed, archive the only retryable ledger, or create confusing repair history even though no note exists.
- **Run policy:** a seal is complete only when both the didrun Git note exists and strict verification exits `0`. Preserve any partial state, retry only after confirming the exact commit/tree/claim set, and never describe the first state as sealed.
- **Suggested fix:** preflight note-ref writability, build the manifest without advancing local state, attach the Git note fail-closed, and append the local seal marker only after publication succeeds. Add an idempotent typed repair path that checks the exact manifest hash, plus a regression test that denies note-ref writes and then retries without losing claims.

## S6-11 — P07B-A2.2 serialized evidence confirms the discipline and recurring friction

- **Observed clean behavior:** the A2.2 implementation checkpoint `32efaaf2f6d9fc58389d48d18219ce03995a2805` used one writer for 20 final events and immediate claims; the corrected descendant `6bf33350944dcdd56a4ceaa70f1d0836203ffb1f` did the same for 11 correction events and claims. Both session chains remained intact, both Git notes exist, both strict checks exited `0`, and every verbatim grade is `TREE-EXACT`. No concurrent-writer or claim-address symptom occurred.
- **Wrapper-output continuation:** the complete Go suite, race suite, 10,000-iteration fuzzing, 117-case architecture self-test, and cumulative verifier produced long quiet intervals before didrun printed only the final wrapper event. A failed corrective verifier invocation and a failed cumulative substep likewise required reading the immutable event blobs to see the recorded error. This reproduces S6-02 under a real source-plus-correction cycle: retention worked, but progressive liveness and direct failure diagnosis did not.
- **Entropy continuation:** plain checkpoint and correction seals stopped on 122 and 53 aggregate high-entropy findings. Each unit first passed an exact staged roster/diff gate and a scoped full-index structured credential-pattern scan that emitted only pattern names and paths on failure and found zero named-pattern matches. Both commits then used the logged redacted-export override, so both notes record `secrets_override: true`. This remains neither a secret-absence finding nor permission to publish source or ledgers.
- **Negative development history:** the preserved corrective development ledger contains an operator shell-quoting error, expected renderer architecture-fingerprint drift, and stale planning-validator README/manifest digests caught by cumulative verification. Those are build/verifier defects rather than didrun defects. They remained nonzero and unclaimed; the tree was repaired, the relevant defensive matrices were rerun, and a fresh frozen-tree ledger supplied the final correction receipts.
- **Platform-policy boundary:** model-generation refusals while drafting an abandoned source-rewrite test design occurred before command execution and are not didrun events, external security actions, or caught product faults. The design was never checked in, claimed, or sealed. A2.2 replaced it with ordinary black-box, property, parity, recovery, fuzz, boundary, and architecture evidence without claiming mutation completeness.
- **Note-publication control:** neither A2.2 final seal reproduced S6-10 in this environment, but both boundaries still required an independent `git notes --ref=didrun show <commit>` success before strict verification. A zero seal exit alone remains insufficient operating policy.
- **Live-session verdict:** under the serialized, chain-intact operating discipline, didrun materially improved attribution by binding exact commands to exact trees and retaining stale-tree or nonzero results as visible history. S6-07 and S6-10 show that the tool alone does not prevent claim misbinding or false publication. Its load-bearing operating constraints remain one writer, fresh ledgers for frozen final trees, explicit note checks, strict loops, external staged-secret review, and manual blob inspection for failures. Concurrency safety, actionable entropy findings, progressive output, and fail-closed note publication remain production-hardening work for didrun itself.

## S6-12 — P07B-B real-session continuation validates serialization, not tool autonomy

- **Observed clean behavior:** P07B-B source commit `eb06bdcf18f8e14db1257e73733afdc05cac045e`, tree `d95c907754f3347bae885a64c98b30ad1ea00256`, used one root writer for 16 final events with an immediate claim after every success. An independent prefix recomputation plus the final direct session view reported `16 events chain intact`; the Git note exists; strict exited `0`; and every verbatim grade is `TREE-EXACT`.
- **Development-history behavior:** the complete 69-event mixed development ledger is preserved separately and supports no final claim. It includes a cumulative-verifier failure that exposed a missing admitted `COUNTERSHAPE_CXX` child-environment binding; after the real environment defect and its self-test expectation were corrected, repeated cumulative runs passed. A final read-only code audit also found missing cancellation proof at the native publication boundary, which was added and rerun before the fresh ledger. These are evidence of the workflow finding ordinary engineering gaps, not didrun defects.
- **Long-command behavior:** race, complete-suite, and cumulative events again produced long quiet intervals before a single final wrapper line. didrun retained the results, but progressive liveness still came from the agent's process polling and user updates rather than the evidence tool itself.
- **Entropy behavior:** the plain source seal stopped on 39 aggregate high-entropy findings after the exact 34-path staged inventory and nine-pattern structured credential scan passed with zero named matches. The logged `--allow-secrets` seal then succeeded and strict visibly reports the redacted-export override. This remains neither a secret-absence result nor permission to publish the source or ledger.
- **Publication behavior:** independent note inspection matched the full commit, tree, 16-event coverage, 16 claims, override flag, and all grades before strict verification. S6-10 did not recur, but the external note check remains mandatory because the installed tool has not been upgraded or repaired during this experiment.
- **Live-session verdict:** didrun behaved usefully under a real long agent session when constrained to one writer, frozen-tree fresh ledgers, immediate claims, external staged-scope review, independent chain closure, note inspection, and strict verification. The successful run does not establish concurrent safety, self-sufficient liveness, actionable entropy classification, automatic claim correctness, or fail-closed note publication.
